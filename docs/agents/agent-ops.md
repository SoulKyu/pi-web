# Agent Ops: agent cards and tasks

## Agent Ops (`lib/agent-ops/`, `app/api/agent-ops/**`, `components/agents/*`)
- **Files:** `overview.ts` (cards from profiles + sessions, `readAgentProfileRef` with a fingerprint cache), `task-store.ts` (JSON task files), `runner.ts` (claims, slots, deadline), `prompt-run.ts` (prompt send, `done`, trigger tool check), `spawn.ts` (`startAgentProfileRun`), `kick.ts` (`kickRunner`, `recoverOnce`), `trigger-store.ts`, `memory-review.ts`. Routes: `overview`, `tasks` (GET/POST), `tasks/[id]` (POST steer, DELETE cancel), `memory` (GET), `memory/[id]/decision` (POST). UI: `AgentsPanel`, `AgentTasks`, `AgentMemory`, `AssignTaskDialog`, `task-view`.
- **Cards are an allowlist.** `AgentCard` never carries `systemPrompt`, `tools` or `filePath`. An orphan card (sessions of a profile no longer defined) sets `orphan: true` and an empty description; the panel renders the translated `agentOps.orphan`, never an English string from the server. The profile-ref cache is cleared at 20000 entries; above that every poll re-reads every file.
- **Terminal states are immutable.** `updateTask` throws on a task already `completed` / `failed` / `cancelled`; the runner's `finish()` re-reads and skips instead. `attachSession` never throws, even on a terminal task.
- **Claims use a `wx` lock** (`claimTask`), re-read after the claim so a task finished in between is not run. Task ids are UUID-guarded in the store (`isValidId`), so a route param can never build a path outside the store.
- **Cancel writes `cancelled` before sending abort.** A cancel during start finds no session to abort, so the runner re-reads the task after `start()` and aborts the late session itself.
- **One `maxRunMs` deadline covers start and run**: a start stuck in an MCP wait or an unanswered extension dialog has no handle yet. On the deadline the task fails with `timeout`, and a session that comes up later is aborted (`abortLateSession`). Every abort is fire-and-forget: its answer is unused, and a hung abort must not hold a slot.
- **The prompt send is not awaited** (`watchPromptRun`). `session.send({ type: "prompt" })` lasts through the MCP wait and the extension preflight (`lib/rpc-manager.ts`), so awaiting it made a hung preflight unabortable (no handle, no `sessionId`, wrapper alive forever). `start()` now returns right after `startRpcSession`; a preflight rejection rejects `done`, and `abort()` reaches the wrapper, which withdraws the MCP wait and cancels extension UI.
- **FIFO:** the runner dequeues oldest first (`listTasks` is newest first for the UI). `kickRunner` is the only runner entry point (task route, recovery, webhook, scheduler). Every run's `finally` calls `onRunEnd` after releasing its slot and claim, and `kickRunner` passes `() => void kickRunner()`: a freed slot starts the next queued task at once. A pass that starts nothing never re-kicks, so a full cap cannot spin.
- **`recoverInterrupted` runs once per process**, on first access of a task route (`recoverOnce`): it fails the runs a dead process left `running`.
- **`spawn.ts` calls `invalidateSessionListCache()` after `startRpcSession`**; the route's call at queue time precedes the session. The route keeps `allowFileRoot(cwd)`.
- **Trigger runs** (pinned profile hash): the pin is re-checked before anything, then `enforceTriggerTools` runs after `waitUntilReady` (extension tools bind late, and the hash cannot see installed extensions) and shuts the session down on any failure, refusal included.
- **Triggers: allowlist and pin** (`trigger-store.ts`, `redact.ts`). Three checks, the last one authoritative: creation (`buildTriggerConfig` → `validateTriggerProfile`, DECLARED tools only, extension tools are invisible before a session exists), ingestion (Task 11: pin drift or missing profile refuses), `start()` (pin recomputed, then `checkActiveTriggerTools` on the session's real `get_tools`). The allowlist is closed (`read grep find ls memory_search memory_save`): a blocklist misses every extension tool that runs code. Only `contentSha256` is compared; scope/filePath are informational. `kickRunner` passes `triggerRunPin(task)`: it fails closed (throws, the runner marks the task `failed`) when an `origin: "trigger"` task has no pin, and ignores the pin of a UI task. Trigger configs live in `<agentDir>/agent-ops/triggers/<uuid>.json` (0600, atomic; `listTriggers` reads only that shape since fire tokens will share the dir). `redact.ts` is a verbatim copy of `pi-mem0/src/redact.ts` (+ `truncate`): always redact, then truncate; server-only (it uses a lookbehind).
- **The panel loads sections independently** (`Promise.allSettled`): a failing tasks request keeps the cards and shows its error, and vice versa.
- **Memory approval** (`memory-review.ts`): pi-mem0 stages each `memory_save` of an agent-profile session as `<PI_MEM0_DIR ?? agentDir/mem0>/staging/<uuid>.json`; pi-web lists those files and writes `<uuid>.decision.json` (`{"approved": bool}`), nothing else: pi-mem0 is the only reader/writer of the mem0 store and applies approved facts in its own 30 s watcher, which runs only in a process where an agent session has started (pi-web runs sessions in-process, so approvals apply once a session has run since the restart). The reader skips any file that is not a well-formed `<uuid>.json` of string fields; `decision` is `applying` while `<uuid>.processing` exists, and `writeDecision` then refuses (409) so a decision cannot race the claim. A decision may be overwritten until then. The id is UUID-checked and the fact re-read before writing. Only the staged queue is shown (no applied memories). Fact text is rendered as plain text; facts of a deleted profile appear under their agent name. The panel loads `memory` as a third independent `allSettled` request.
- **Scheduler and webhook** (`scheduler.ts`, `webhook.ts`, `hook-path.ts`, `app/api/agent-ops/triggers/[id]/hook`). `startScheduler` (from `instrumentation-node.ts`, one per process via `globalThis.__agentOpsScheduler`) recovers interrupted tasks, kicks, then ticks every 60 s: purge fire tokens, `pruneTasks` (terminal tasks older than 14 days, at most hourly), fire every enabled `everyMinutes` trigger, kick. Triggers are re-read each tick (no snapshot). Fire tokens are `wx` files in the triggers dir: payload `<id>.<bucket>_<hash16>` (webhook dedup) and `<id>.sched.<bucket>` (scheduled fires bypass payload dedup, else `everyMinutes < dedupWindowMs` swallows fires). `maxActiveTasks` is checked before the payload token, so a refused payload does not consume it. `purgeStaleFireTokens` deletes tokens older than max(24 h, 2 × window); tokens of a deleted trigger after 24 h; `<uuid>.json` never.
- **Webhook is fail-closed.** `proxy.ts` exempts exactly `POST /api/agent-ops/triggers/<uuid>/hook` (`isAgentOpsHookRequest`), before any Authorization handling so a wrong header never feeds the login throttle; the host/origin check still runs first. `handleHook`: hook throttle (`globalThis.__agentOpsHookThrottle`, never the login state) → unknown id is 404 and counts as a failure → a trigger without `webhookSecret` is refused (403) before any comparison → `x-agent-ops-secret` compared as `timingSafeEqual` of two sha256 digests → body read from the stream with a 64 KB cap (413; `content-length` is not trusted) → JSON if the content type says so, else `{ text }` → `ingestTriggerPayload` (enabled, pin check, cap, dedup): 202 `{ taskId }` + kick, or 409 `{ reason }`. Payloads are redacted, truncated to 8000 chars and fenced in `<untrusted_payload>`; `fenceUntrusted` defuses that tag in any case or spacing. Responses never echo the secret or the payload.
