# Agent Ops: tasks, triggers and memory approval

## Agent Ops (`lib/agent-ops/`, `app/api/agent-ops/**`, `components/agents/*`)
- **Files:** `task-store.ts` (JSON task files), `runner.ts` (claims, slots, deadline), `prompt-run.ts` (prompt send, `done`, trigger tool check), `spawn.ts` (`startAgentProfileRun`), `kick.ts` (`kickRunner`, `isThreadBusy`, `handleTaskEnd`, `recoverOnce`), `trigger-store.ts`, `memory-review.ts`, `task-list.ts`; thread-target tasks live in `lib/agents/{queue,thread-run}.ts` (long-term-agents.md). Routes: `tasks/[id]` (POST steer, DELETE cancel), `memory` (GET), `memory/[id]/decision` (POST). UI: `AgentTasks`, `AgentMemory`, `AgentTriggers`, `TriggerDialog`, `AgentSpaceLeft`, `task-view`. The agent-facing parts (space, thread, event cards, webhook summary and read-only runs) are in long-term-agents.md.
- **Settings (`settings.ts`)**: `~/.pi/agent/agent-ops/settings.json`, every knob of the 2026-10-07 roadmap (automatic-run cap, free-memory floor, pause, quiet hours); defaults on absence; validated patches only. Route: `settings` (GET, PUT).
- **Terminal states are immutable.** `updateTask` throws on a task already `completed` / `failed` / `cancelled`; the runner's `finish()` re-reads and skips instead. `attachSession` never throws, even on a terminal task.
- **Claims use a `wx` lock** (`claimTask`), re-read after the claim so a task finished in between is not run. Task ids are UUID-guarded in the store (`isValidId`), so a route param can never build a path outside the store.
- **Cancel writes `cancelled` before sending abort.** A cancel during start finds no session to abort, so the runner re-reads the task after `start()` and aborts the late session itself.
- **One `maxRunMs` deadline covers start and run**: a start stuck in an MCP wait or an unanswered extension dialog has no handle yet. On the deadline the task fails with `timeout`, and a session that comes up later is aborted (`abortLateSession`). Every abort is fire-and-forget: its answer is unused, and a hung abort must not hold a slot.
- **Run guard** (`lib/agent-ops/run-guard.ts`): `watchPromptRun` observes every event first and, on a trip, rejects `done` with a `RunGuardError` (the task fails with its message) and sends a fire-and-forget abort; the thread stays open. Limits are global constants (`DEFAULT_RUN_GUARD_LIMITS`): 5 identical consecutive top-level tool calls (`toolName` + JSON args), 150 top-level tool calls, 60 assistant turns. Nested calls (`parentToolCallId`) count for nothing. Per-profile limits are not built: YAGNI until a real false positive.
- **The prompt send is not awaited** (`watchPromptRun`). `session.send({ type: "prompt" })` lasts through the MCP wait and the extension preflight (`lib/rpc-manager.ts`), so awaiting it made a hung preflight unabortable (no handle, no `sessionId`, wrapper alive forever). `start()` now returns right after `startRpcSession`; a preflight rejection rejects `done`, and `abort()` reaches the wrapper, which withdraws the MCP wait and cancels extension UI.
- **FIFO, two runners.** A runner dequeues oldest first (`listTasks` is newest first for the UI). `kickRunner` is the only entry point (task route, recovery, webhook, scheduler) and starts two `runPendingTasks` passes over the same store: isolated (`slotKey: "__agentOpsRunning"`, `select: selectIsolatedTasks`) and thread (`slotKey: "__agentOpsThreadRunning"`, `select: selectThreadTasks`, one per agent). Both get the same `capacity` (`capacity.ts` `automaticCapacity`, settings read once per kick): `maxAutomaticRuns` minus the runs of both runners, 0 while `/proc/meminfo` MemAvailable is under `minFreeMb` (unreadable = no floor); a runner starts `min(capacity(), maxConcurrent - own running)`. Both passes read it before incrementing, so a brief overshoot of one run is possible; the 60 s re-kick settles it. What weighs is MCP stdio servers, subagents and the bge-m3 embedder, not the in-process sessions. `slotKey` names the `globalThis` slot set, so the runners never count each other's runs; `select` picks from the queued list (and the full list). Every run's `finally` calls `onTaskEnd` (after the claim is released, errors swallowed; `handleTaskEnd` pushes a failed task of an agent) then `onRunEnd` (`() => void kickRunner()`): a freed slot starts the next queued task at once. A pass that starts nothing never re-kicks, so a full cap cannot spin.
- **`recoverInterrupted` runs once per process**, on first access of a task route (`recoverOnce`) and in `startScheduler`: it fails the runs a dead process left `running`. After an HMR edit of `scheduler.ts` / `kick.ts` the first module's interval keeps ticking until a restart. Never run this worktree's dev server next to the live `:30141` one: two schedulers and runners would share `~/.pi/agent/agent-ops`.
- **The task list is bounded** (`task-list.ts`, `shapeTaskList`): `GET /api/agents/[name]/tasks` (the only caller of `shapeTaskList`) returns every queued/running task plus the newest 200 others, newest first, as `{ tasks, truncated? }`. Items carry no `prompt` (the title is its first line) and `result` / `error` are clipped to 2000 chars with `…`; the session holds the full text. A trigger's history renders only while its `<details>` is open (the list is polled every 5 s and already shown in the Tasks section).
- **`spawn.ts` calls `invalidateSessionListCache()` after `startRpcSession`**.
- **Trigger runs** (pinned profile hash, isolated runs only: webhooks): the pin is re-checked before anything, then `enforceTriggerTools` runs after `waitUntilReady` (extension tools bind late, and the hash cannot see installed extensions) and shuts the session down on any failure, refusal included.
- **Triggers: allowlist and pin** (`trigger-store.ts`, `redact.ts`). Three checks, the last one authoritative (they guard webhook runs; a schedule fire goes to the thread and only the first two apply): creation (`buildTriggerConfig` → `validateTriggerProfile`: the profile must be long-term; tools are no longer checked here, the run is narrowed instead), ingestion (Task 11: pin drift or missing profile refuses), `start()` (pin recomputed, then `checkActiveTriggerTools` on the session's real `get_tools`; the session is also created with `agentProfileTools`). The allowlist is closed (`read grep find ls memory_search memory_save`): a blocklist misses every extension tool that runs code. Only `contentSha256` is compared; scope/filePath are informational. `kickRunner` passes `triggerRunPin(task)`: it fails closed (throws, the runner marks the task `failed`) when an `origin: "trigger"` task has no pin, and ignores the pin of a UI task. Trigger configs live in `<agentDir>/agent-ops/triggers/<uuid>.json` (0600, atomic; `listTriggers` reads only that shape since fire tokens will share the dir). `redact.ts` is a verbatim copy of `pi-mem0/src/redact.ts` (+ `truncate`): always redact, then truncate; server-only (it uses a lookbehind).
- **Memory approval** (`memory-review.ts`): pi-mem0 stages each `memory_save` of an agent-profile session as `<PI_MEM0_DIR ?? agentDir/mem0>/staging/<uuid>.json`; pi-web lists those files and writes `<uuid>.decision.json` (`{"approved": bool}`), nothing else: pi-mem0 is the only reader/writer of the mem0 store and applies approved facts in its own 30 s watcher, which runs only in a process where an agent session has started (pi-web runs sessions in-process, so approvals apply once a session has run since the restart). The reader skips any file that is not a well-formed `<uuid>.json` of string fields; `decision` is `applying` while a fresh `<uuid>.processing` exists, and `writeDecision` then refuses (409) so a decision cannot race the claim. A `.processing` whose mtime is older than 10 minutes is stale (a crashed apply; pi-mem0's README says to re-approve it from pi-web): it no longer counts as `applying`, the buttons come back and `writeDecision` is allowed, pi-mem0's next pass renames the new decision over it. Caveat: a rename keeps the decision file's mtime, so a decision written long before pi-mem0 claims it can look stale while it is being applied. A decision may be overwritten until then. The id is UUID-checked and the fact re-read before writing. Only the staged queue is shown (no applied memories). Fact text is rendered as plain text; facts of a deleted profile appear under their agent name. It is shown in the agent space's right panel through `GET /api/agents/[name]/memory`; `GET /api/agent-ops/memory` without `?agent=` leaves long-term agents' facts out.
- **Scheduler and webhook** (`scheduler.ts`, `webhook.ts`, `hook-path.ts`, `app/api/agent-ops/triggers/[id]/hook`). `startScheduler` (from `instrumentation-node.ts` through dynamic imports, not awaited, errors logged and never rethrown: a failure in `kick` → `rpc-manager` must not stop the server from booting; one per process via `globalThis.__agentOpsScheduler`) recovers interrupted tasks, kicks, then ticks every 60 s: purge fire tokens, `pruneTasks` (terminal tasks older than 14 days, at most hourly), fire every enabled `everyMinutes` trigger (same admission as the webhook: enabled, profile resolvable, pin matches; a refused fire creates no task, keeps its bucket token and logs once per bucket; one trigger's error never stops the others), kick. Triggers are re-read each tick (no snapshot). Fire tokens are `wx` files in the triggers dir: payload `<id>.<bucket>_<hash16>` (webhook dedup) and `<id>.sched.<bucket>` (scheduled fires bypass payload dedup, else `everyMinutes < dedupWindowMs` swallows fires). `maxActiveTasks` is checked before the payload token, so a refused payload does not consume it. `purgeStaleFireTokens` deletes tokens older than max(24 h, 2 × window); tokens of a deleted trigger after 24 h; `<uuid>.json` never.
- **Fire journal and `planIngestion`** (`trigger-log.ts`, `scheduler.ts`, `app/api/agent-ops/triggers/[id]/log`). `planIngestion(trigger, body, now, activeTasks)` is pure (no file, no token): admission refusal, then the cap refusal (`too many active tasks for this trigger`), else `accepted` with the prompt, token name, payload hash and bucket; callers pass `activeTasks` so dry-runs and later caps reuse it. `ingestTriggerPayload` = plan → claim the token → `createTriggerTask` → journal line; a cap refusal whose token already exists is reported as `duplicate within dedup window` (existing token = same payload hash already ingested in this bucket, so the call is a replay whatever the earlier task's state). The journal is `<triggersDir>/<id>.log.jsonl` (0600 `appendFileSync`, one line per verdict; past 600 lines it is rewritten atomically to the last 500; `readTriggerLog` is newest first, caps at 500, skips junk lines; both never throw, `listTriggers` and the token purge ignore the file). Scheduled fires journal `accepted` (with `taskId`) and journal a refusal once per bucket (the `logRefusalOnce` map), so a stuck cap adds no line per tick. Tasks carry `fireReason { source, bucket?, payloadHash? }` and schedule/task cards show it. **Never journaled**: hook calls refused before ingestion (`401/403 (secret) and 413 (body too large)`, not `404`): `handleHook` only counts them in memory per known trigger (`rejectedUnauthenticatedCount`, reset on restart), shown by the log route as `rejectedUnauthenticated`; secrets and payload text never enter the journal (hash only). The journal of a deleted trigger is removed when the trigger is deleted.
- **Dry-run and manual fire** (`POST …/triggers/[id]/dry-run`, `POST …/[id]/fire`, `fireTriggerNow`). Both behind the session; the hook route is untouched. Dry-run = `planIngestion` with the live `activeTaskCount` plus `tokenFree` (does the token file exist), `target` (secret → `isolated`, else `thread`), `pinStatus` and `tools` (`TRIGGER_TOOL_ALLOWLIST` for isolated, `[]` for a thread target: it runs with the agent's own tools): it writes nothing (no token, task or journal line) and calls no model. `fireTriggerNow` refuses on admission, then pause (`agent paused`, global or per agent), then the cap (same reason as the plan), and journals `source: "manual"` for both outcomes. **No dedup token**: two manual fires with the same payload both run. A trigger with a secret creates an isolated `webhook` task from the fenced payload (`(manual fire, no payload)` when none); otherwise its thread `schedule` task from the template. `fire` answers 202 `{ taskId }` + kick, or 409 `{ reason }`. UI: Test (inline panel, prompt clipped to 40 lines) and Run now (confirm) per row.
- **Webhook is fail-closed.** `proxy.ts` exempts exactly `POST /api/agent-ops/triggers/<uuid>/hook` (`isAgentOpsHookRequest`), before any Authorization handling so a wrong header never feeds the login throttle; the host/origin check still runs first. `handleHook`: per-trigger hook throttle (`globalThis.__agentOpsHookThrottles`, one state per known trigger; unknown or invalid ids share a separate state no known trigger consults, so a flood on one id cannot drop another trigger's alerts; never the login state) → unknown id is 404 and counts as a failure on that shared state → a trigger without a valid `webhookSecretSha256` is refused (403) before any comparison → `x-agent-ops-secret` is hashed and compared as `timingSafeEqual` against the stored digest → body read from the stream with a 64 KB cap (413; `content-length` is not trusted; a stream that errors, e.g. the client left mid-body, is a 400) → JSON if the content type says so, else `{ text }` → `ingestTriggerPayload` (enabled, pin check, cap, dedup): 202 `{ taskId }` + kick, or 409 `{ reason }`. Payloads are redacted, truncated to 8000 chars and fenced in `<untrusted_payload>`; `fenceUntrusted` defuses that tag in any case or spacing. Responses never echo the secret or the payload.
- **Trigger management** (`trigger-api.ts`, `app/api/agent-ops/triggers/**`, `AgentTriggers`, `TriggerDialog`, `TriggerSecretDialog`). Behind the session (only `/hook` is exempt). Secrets are server-generated only (`randomBytes(32)` base64url): `buildTriggerConfig` refuses any client `webhookSecret`; the secret is returned once, by create with `webhook: true` or by `POST …/<id>/secret` (rotate; also the way to give a first secret to a trigger without one; it drops that trigger's hook throttle state). **Only the hex sha256 is stored** (`webhookSecretSha256`): the plaintext never touches disk. A trigger file still holding a legacy plaintext `webhookSecret` has no digest, so its webhook is refused (403, fail closed) until the secret is rotated, which also drops the plaintext field. Every response goes through `toPublicTrigger` (`hasWebhookSecret` from the digest, `pinStatus`, never the secret or the digest, legacy plaintext included). `buildTriggerConfig` also refuses a non-boolean `enabled` and turns a vanished profile file into an error instead of a throw. `patchTrigger` accepts a closed field list (unknown fields, `webhookSecret` included, are refused; `everyMinutes: null` clears the schedule, while `null` for `dedupWindowMs` / `maxActiveTasks` is refused: it would skip the defaults and be saved as is) and renews the pin only when `profile` changes or on `{ repin: true }`: a toggle or rename of a trigger whose profile drifted or vanished still works, and never silently accepts the drift.
- **Triggers belong to long-term agents.** `trigger.profile` is the agent name, with no `cwd`: runs happen in `triggerHome` (the agent home). The pin and every re-resolution (`triggerPinStatus`, `resolveIn`, `startAgentProfileRun`) use the GLOBAL profile (`resolveLongTermProfile`): the agent can write its home, so a `<home>/.pi/agents/<name>.md` must never shadow it. Scheduled fires create a `target: "thread"` task with the raw template (nothing external in it); webhook payloads stay `isolated` and fenced. An isolated run passes `agentProfileTools` (the allowlist) with no trust; `startRpcSession` then also resolves globally and only in the agent home, and applies the override to new sessions only. `PATCH /api/agents/[name]` re-pins the agent's triggers (`repinTriggersOfAgent`), `DELETE` removes them first.
- **Profile drift is visible.** `triggerPinStatus` (`trigger-store.ts`, the scheduler's admission check, never throws: an unresolvable or unreadable profile is `missing`) feeds `pinStatus: "ok" | "drift" | "missing"` on every public trigger. The row shows a translated badge saying fires are refused; a `drift` row gets a Re-pin button (confirm, then `PATCH { repin: true }`). `repin` re-resolves the agent's global profile and re-runs the creation check (`validateTriggerProfile`): a profile that is no longer long-term is refused and the old pin stays. `missing` has no button: restore the profile or edit the trigger. History is the tasks list filtered by `triggerId` on the client; triggers are loaded and polled every 10 s by `AgentSpaceLeft`. The secret dialog keeps the secret in React state only and closes on Escape, not on a backdrop click.
- **Pause** (`settings.paused`, `pausedAgents`): scheduler skips, webhook 503 (no token consumed), selectors skip, thread runs refuse, running tasks of the scope are aborted when the pause is set; user turns are never blocked.
- **Run registry** (`run-registry.ts`): `~/.pi/agent/agent-ops/runs.jsonl`, one line per run (tasks through the runner, user turns of trusted threads through the wrapper), usage counted by `run-usage.ts` from the run's own events; `billing` (`subscription` for `claude-bridge`, `api` for any other provider, `unknown` without one) and `costEquivalent` (subscription only, `priceRecord()` in `lib/cost-equivalent.ts`, shared by the runner and the thread tracker) sit beside `usage.cost`, never summed into it; rotated past 10 MiB; `task.usage` holds the same numbers, except when a cancel won the terminal write: then it is absent and the registry is the source of truth. Exported to Grafana by promtail/Alloy, never by a scrape of the sessions. A thread event turn is recorded by the runner only: the wrapper skips its user-turn record only for a turn started by the runner's own prompt (`origin: "agent-ops"`, counted in `pendingRunnerPrompts`), never because a task is `running`. A run whose terminal write lost to a cancel is still recorded, with the winning status.
- **Health gauges** (`health.ts`, `GET /api/agent-ops/health`, dot under `+` in `AgentRail`). Pure `collectHealth` / `healthLevel` over: `globalThis.__agentOpsLastTick` (set as the last statement of every `runSchedulerTick`, paused or failed included), both runners' `runningCount`, `countAliveRpcSessions()`, `memAvailableMb()`, `settings.paused`, and `getExtensionErrorStatuses()` (alive wrappers' extension statuses starting with "error"/"failed"). `down`: last tick over 3 min old; `warn`: no tick yet (the first tick comes 60 s after `startScheduler`, so a fresh process is not red), extension errors, `freeMb < 1500` or paused; else `ok`. The rail polls every 30 s while visible. RAM, services and TCP probes are node_exporter's job.
