# Agent Ops: tasks, triggers and memory approval

## Agent Ops (`lib/agent-ops/`, `app/api/agent-ops/**`, `components/agents/*`)
- **Files:** `task-store.ts` (JSON task files), `runner.ts` (claims, slots, deadline), `prompt-run.ts` (prompt send, `done`, trigger tool check), `spawn.ts` (`startAgentProfileRun`), `kick.ts` (`kickRunner`, `isThreadBusy`, `handleTaskEnd`, `recoverOnce`), `trigger-store.ts`, `memory-review.ts`, `task-list.ts`; thread-target tasks live in `lib/agents/{queue,thread-run}.ts` (long-term-agents.md). Routes: `tasks/[id]` (POST steer, DELETE cancel), `memory` (GET), `memory/[id]/decision` (POST). UI: `AgentTasks`, `AgentMemory`, `AgentTriggers`, `TriggerDialog`, `AgentSpaceLeft`, `task-view`. The agent-facing parts (space, thread, event cards, webhook summary and read-only runs) are in long-term-agents.md.
- **Settings (`settings.ts`)**: `~/.pi/agent/agent-ops/settings.json`, every knob of the 2026-10-07 roadmap (automatic-run cap, free-memory floor, pause, quiet hours); defaults on absence; validated patches only. Route: `settings` (GET, PUT).
- **Terminal states are immutable.** `updateTask` throws on a task already `completed` / `failed` / `cancelled`; the runner's `finish()` re-reads and skips instead. `attachSession` never throws, even on a terminal task.
- **Claims use a `wx` lock** (`claimTask`), re-read after the claim so a task finished in between is not run. Task ids are UUID-guarded in the store (`isValidId`), so a route param can never build a path outside the store.
- **Global tasks board and the parent link** (Task 49, `app/api/agent-ops/tasks/route.ts`, `components/agents/TasksBoard.tsx`). `GET /api/agent-ops/tasks` is `shapeTaskList(listTasks())` for every agent (no prompts, `no-store`; GET only, tasks are created through the per-agent route). The rail's "⧉ Tasks" button opens the board: tasks grouped by `agent` (legacy tasks under "other"), `AgentTasks` per group, "requested by X" with a link that opens that agent. The board fetches on open and every 5 s only while open (interval cleared on close). `agent_delegate` sets `parentTaskId` to the caller's currently RUNNING thread task (`agent === from`, `target === "thread"`) when there is one, else the field is absent. **Cancel cascade:** DELETE of a task also cancels its QUEUED children (`cancelQueuedChildren`, `parentTaskId === id`) and answers `cancelledChildren: n`; running children are left alone (cancel them yourself), terminal ones are immutable.
- **Cancel writes `cancelled` before sending abort.** A cancel during start finds no session to abort, so the runner re-reads the task after `start()` and aborts the late session itself.
- **One `maxRunMs` deadline covers start and run**: a start stuck in an MCP wait or an unanswered extension dialog has no handle yet. On the deadline the task fails with `timeout`, and a session that comes up later is aborted (`abortLateSession`). Every abort is fire-and-forget: its answer is unused, and a hung abort must not hold a slot.
- **Run guard** (`lib/agent-ops/run-guard.ts`): `watchPromptRun` observes every event first and, on a trip, rejects `done` with a `RunGuardError` (the task fails with its message) and sends a fire-and-forget abort; the thread stays open. Limits are global constants (`DEFAULT_RUN_GUARD_LIMITS`): 5 identical consecutive top-level tool calls (`toolName` + JSON args), 150 top-level tool calls, 60 assistant turns. Nested calls (`parentToolCallId`) count for nothing. Per-profile limits are not built: YAGNI until a real false positive.
- **The prompt send is not awaited** (`watchPromptRun`). `session.send({ type: "prompt" })` lasts through the MCP wait and the extension preflight (`lib/rpc-manager.ts`), so awaiting it made a hung preflight unabortable (no handle, no `sessionId`, wrapper alive forever). `start()` now returns right after `startRpcSession`; a preflight rejection rejects `done`, and `abort()` reaches the wrapper, which withdraws the MCP wait and cancels extension UI.
- **FIFO, two runners.** A runner dequeues oldest first (`listTasks` is newest first for the UI). `kickRunner` is the only entry point (task route, recovery, webhook, scheduler) and starts two `runPendingTasks` passes over the same store: isolated (`slotKey: "__agentOpsRunning"`, `select: selectIsolatedTasks`) and thread (`slotKey: "__agentOpsThreadRunning"`, `select: selectThreadTasks`, one per agent). Both get the same `capacity` (`capacity.ts` `automaticCapacity`, settings read once per kick): `maxAutomaticRuns` minus the runs of both runners, 0 while `/proc/meminfo` MemAvailable is under `minFreeMb` (unreadable = no floor); a runner starts `min(capacity(), maxConcurrent - own running)`. Both passes read it before incrementing, so a brief overshoot of one run is possible; the 60 s re-kick settles it. What weighs is MCP stdio servers, subagents and the bge-m3 embedder, not the in-process sessions. `slotKey` names the `globalThis` slot set, so the runners never count each other's runs; `select` picks from the queued list (and the full list). Every run's `finally` calls `onTaskEnd` (after the claim is released, errors swallowed; `handleTaskEnd` pushes a failed task of an agent; for an isolated run it awaits the summary card first and the push url is `/?agent=<name>&entry=<card id>`, otherwise `/?agent=<name>`; a task with `deliverTo` then appends a `delegation` card to that agent's thread (existing card → delegation card → failure push; a card only, never a prompt, errors logged); the order of cancel/steer is untouched) then `onRunEnd` (`() => void kickRunner()`): a freed slot starts the next queued task at once. A pass that starts nothing never re-kicks, so a full cap cannot spin.
- **`recoverInterrupted` runs once per process**, on first access of a task route (`recoverOnce`) and in `startScheduler`: it fails the runs a dead process left `running`. After an HMR edit of `scheduler.ts` / `kick.ts` the first module's interval keeps ticking until a restart. Never run this worktree's dev server next to the live `:30141` one: two schedulers and runners would share `~/.pi/agent/agent-ops`.
- **The task list is bounded** (`task-list.ts`, `shapeTaskList`): `GET /api/agents/[name]/tasks` (and `GET /api/agent-ops/tasks`, Task 49) returns every queued/running task plus the newest 200 others, newest first, as `{ tasks, truncated? }`. Items carry no `prompt` (the title is its first line) and `result` / `error` are clipped to 2000 chars with `…`; the session holds the full text. A trigger's history renders only while its `<details>` is open (the list is polled every 5 s and already shown in the Tasks section).
- **`spawn.ts` calls `invalidateSessionListCache()` after `startRpcSession`**.
- **Trigger runs** (pinned profile hash, isolated runs only: webhooks): the pin is re-checked before anything, then `enforceTriggerTools` runs after `waitUntilReady` (extension tools bind late, and the hash cannot see installed extensions) and shuts the session down on any failure, refusal included.
- **Triggers: allowlist and pin** (`trigger-store.ts`, `redact.ts`). Three checks, the last one authoritative (they guard webhook runs; a schedule fire goes to the thread and only the first two apply): creation (`buildTriggerConfig` → `validateTriggerProfile`: the profile must be long-term; tools are no longer checked here, the run is narrowed instead), ingestion (Task 11: pin drift or missing profile refuses), `start()` (pin recomputed, then `checkActiveTriggerTools` on the session's real `get_tools`; the session is also created with `agentProfileTools`). The allowlist is closed (`read grep find ls memory_search memory_save`): a blocklist misses every extension tool that runs code. **A task or trigger `tools` subset can only shrink it**, also at run start (Task 48: `spawn.ts` narrows and `enforceTriggerTools` checks whenever `task.tools` is set, pin or not, so a UI review task `kind: "review"` with `tools` is held to its subset too): `checkActiveTriggerTools(active, allowed = allowlist)` refuses a tool outside the allowlist OR outside `allowed`, and `spawn.ts` drops non-allowlist names from `agentProfileTools` (a hand-edited or legacy file with `tools: ["bash"]` yields `[]`, never bash). Only `contentSha256` is compared; scope/filePath are informational. `kickRunner` passes `triggerRunPin(task)`: it fails closed (throws, the runner marks the task `failed`) when an `origin: "trigger"` task has no pin, and ignores the pin of a UI task. Trigger configs live in `<agentDir>/agent-ops/triggers/<uuid>.json` (0600, atomic; `listTriggers` reads only that shape since fire tokens will share the dir). `redact.ts` is a verbatim copy of `pi-mem0/src/redact.ts` (+ `truncate`): always redact, then truncate; server-only (it uses a lookbehind).
- **Memory approval** (`memory-review.ts`): pi-mem0 stages each `memory_save` of an agent-profile session as `<PI_MEM0_DIR ?? agentDir/mem0>/staging/<uuid>.json`; pi-web lists those files and writes `<uuid>.decision.json` (`{"approved": bool}`), nothing else: pi-mem0 is the only reader/writer of the mem0 store and applies approved facts in its own 30 s watcher, which runs only in a process where an agent session has started (pi-web runs sessions in-process, so approvals apply once a session has run since the restart). The reader skips any file that is not a well-formed `<uuid>.json` of string fields; `decision` is `applying` while a fresh `<uuid>.processing` exists, and `writeDecision` then refuses (409) so a decision cannot race the claim. A `.processing` whose mtime is older than 10 minutes is stale (a crashed apply; pi-mem0's README says to re-approve it from pi-web): it no longer counts as `applying`, the buttons come back and `writeDecision` is allowed, pi-mem0's next pass renames the new decision over it. Caveat: a rename keeps the decision file's mtime, so a decision written long before pi-mem0 claims it can look stale while it is being applied. A decision may be overwritten until then. The id is UUID-checked and the fact re-read before writing. Only the staged queue is shown (no applied memories). Fact text is rendered as plain text; facts of a deleted profile appear under their agent name. It is shown in the agent space's right panel through `GET /api/agents/[name]/memory`; `GET /api/agent-ops/memory` without `?agent=` leaves long-term agents' facts out.
- **Scheduler and webhook** (`scheduler.ts`, `webhook.ts`, `hook-path.ts`, `app/api/agent-ops/triggers/[id]/hook`). `startScheduler` (from `instrumentation-node.ts` through dynamic imports, not awaited, errors logged and never rethrown: a failure in `kick` → `rpc-manager` must not stop the server from booting; one per process via `globalThis.__agentOpsScheduler`) recovers interrupted tasks, kicks, then ticks every 60 s: purge fire tokens, `pruneTasks` (terminal tasks older than 14 days, at most hourly), fire every enabled `everyMinutes` trigger (same admission as the webhook: enabled, profile resolvable, pin matches; a refused fire creates no task, keeps its bucket token and logs once per bucket; one trigger's error never stops the others), kick. Triggers are re-read each tick (no snapshot). Fire tokens are `wx` files in the triggers dir: payload `<id>.<bucket>_<hash16>` (webhook dedup) and `<id>.sched.<bucket>` (scheduled fires bypass payload dedup, else `everyMinutes < dedupWindowMs` swallows fires). `maxActiveTasks` is checked before the payload token, so a refused payload does not consume it. `purgeStaleFireTokens` deletes tokens older than max(24 h, 2 × window); tokens of a deleted trigger after 24 h; `<uuid>.json` never.
- **Fire journal and `planIngestion`** (`trigger-log.ts`, `scheduler.ts`, `app/api/agent-ops/triggers/[id]/log`). `planIngestion(trigger, body, now, activeTasks)` is pure (no file, no token): admission refusal, then the cap refusal (`too many active tasks for this trigger`), else `accepted` with the prompt, token name, payload hash and bucket; callers pass `activeTasks` so dry-runs and later caps reuse it. `ingestTriggerPayload` = plan → claim the token → `createTriggerTask` → journal line; a cap refusal whose token already exists is reported as `duplicate within dedup window` (existing token = same payload hash already ingested in this bucket, so the call is a replay whatever the earlier task's state). The journal is `<triggersDir>/<id>.log.jsonl` (0600 `appendFileSync`, one line per verdict; past 600 lines it is rewritten atomically to the last 500; `readTriggerLog` is newest first, caps at 500, skips junk lines; both never throw, `listTriggers` and the token purge ignore the file). Scheduled fires journal `accepted` (with `taskId`) and journal a refusal once per bucket (the `logRefusalOnce` map), so a stuck cap adds no line per tick. Tasks carry `fireReason { source, bucket?, payloadHash? }` and schedule/task cards show it. **Never journaled**: hook calls refused before ingestion (`401/403 (secret) and 413 (body too large)`, not `404`): `handleHook` only counts them in memory per known trigger (`rejectedUnauthenticatedCount`, reset on restart), shown by the log route as `rejectedUnauthenticated`; secrets and payload text never enter the journal (hash only). The journal of a deleted trigger is removed when the trigger is deleted.
- **Per-trigger run settings** (Task 17, `trigger-store.ts`, `scheduler.ts`, `spawn.ts`, `runner.ts`). A trigger may carry `runTarget` (`thread` default | `isolated`, schedule triggers only; a trigger with a webhook secret is always isolated), `model` (`provider/modelId`, `splitModel` ≠ null), `tools` (non-empty, deduplicated strict subset of `TRIGGER_TOOL_ALLOWLIST`: the allowlist can only shrink per trigger, error `tools must be a subset of the trigger allowlist`) and `maxRunMs` (integer 60 000..3 600 000); PATCH clears each with `null`. `createTriggerTask` copies `model`, `tools`, `maxRunMs` onto every task it creates; a schedule fire with `runTarget: "isolated"` makes a `target: "isolated"`, `kind: "schedule"` task whose prompt is the raw template (the user's own text, no fence). `startAgentProfileRun(task, beforePrompt?, deps?)` passes `agentProfileTools: task.tools ?? allowlist` and `initialModel` from `task.model`; `enforceTriggerTools(session, task.tools)` checks the live session against the subset; `deps.startRpcSession` is the test seam. The runner deadline is `task.maxRunMs ?? deps.maxRunMs ?? DEFAULT_MAX_RUN_MS`. UI: `TriggerDialog` (Run in, model, six tool checkboxes where all checked = no subset, max duration in minutes).
- **Dry-run and manual fire** (`POST …/triggers/[id]/dry-run`, `POST …/[id]/fire`, `fireTriggerNow`). Both behind the session; the hook route is untouched. Dry-run = `planIngestion` with the live `activeTaskCount` plus `tokenFree` (does the token file exist), `target` (secret → `isolated`, else `runTarget ?? thread`), `prompt` (the raw template for a schedule trigger, the fenced prompt only for a webhook one), `pinStatus`, a `refused` verdict `agent paused` while the agent or everything is paused, and `tools` (`trigger.tools ?? TRIGGER_TOOL_ALLOWLIST` for isolated, `[]` for a thread target: it runs with the agent's own tools): it writes nothing (no token, task or journal line) and calls no model. `fireTriggerNow` refuses on admission, then pause (`agent paused`, global or per agent), then the cap (same reason as the plan), and journals `source: "manual"` for both outcomes. **No dedup token**: two manual fires with the same payload both run. A trigger with a secret creates an isolated `webhook` task from the fenced payload (`(manual fire, no payload)` when none); otherwise its `schedule` task from the template (thread, or isolated with `runTarget: "isolated"`). `fire` answers 202 `{ taskId }` + kick, or 409 `{ reason }`. UI: Test (inline panel, prompt clipped to 40 lines) and Run now (confirm) per row.
- **Webhook is fail-closed.** `proxy.ts` exempts exactly `POST /api/agent-ops/triggers/<uuid>/hook` (`isAgentOpsHookRequest`), before any Authorization handling so a wrong header never feeds the login throttle; the host/origin check still runs first. `handleHook`: per-trigger hook throttle (`globalThis.__agentOpsHookThrottles`, one state per known trigger; unknown or invalid ids share a separate state no known trigger consults, so a flood on one id cannot drop another trigger's alerts; never the login state) → unknown id is 404 and counts as a failure on that shared state → a trigger without a valid `webhookSecretSha256` is refused (403) before any comparison → `x-agent-ops-secret` is hashed and compared as `timingSafeEqual` against the stored digest → body read from the stream with a 64 KB cap (413; `content-length` is not trusted; a stream that errors, e.g. the client left mid-body, is a 400) → JSON if the content type says so, else `{ text }` → `ingestTriggerPayload` (enabled, pin check, cap, dedup): 202 `{ taskId }` + kick, or 409 `{ reason }`. Payloads are redacted, truncated to 8000 chars and fenced in `<untrusted_payload id="<nonce>">…</untrusted_payload id="<nonce>">` (per-task 8-hex nonce from `newFenceId()`, also named in the closing sentence); `fenceTag(text, "untrusted_payload")` (shared with `lib/agents/untrusted-content.ts`) strips format characters and defuses that tag in any case or spacing. Responses never echo the secret or the payload. **Payload `severity` is chosen by the sender** (an alert body says `critical`); the webhook secret is the only barrier, and a `critical` payload bypasses quiet hours. A critical alert is never deferred and stays capped by `maxActiveTasks` (and the daily budget and run cap); deferred ones are bounded by `MAX_DEFERRED_PER_TRIGGER`.
- **Trigger management** (`trigger-api.ts`, `app/api/agent-ops/triggers/**`, `AgentTriggers`, `TriggerDialog`, `TriggerSecretDialog`). Behind the session (only `/hook` is exempt). Secrets are server-generated only (`randomBytes(32)` base64url): `buildTriggerConfig` refuses any client `webhookSecret`; the secret is returned once, by create with `webhook: true` or by `POST …/<id>/secret` (rotate; also the way to give a first secret to a trigger without one; it drops that trigger's hook throttle state). **Only the hex sha256 is stored** (`webhookSecretSha256`): the plaintext never touches disk. A trigger file still holding a legacy plaintext `webhookSecret` has no digest, so its webhook is refused (403, fail closed) until the secret is rotated, which also drops the plaintext field. Every response goes through `toPublicTrigger` (`hasWebhookSecret` from the digest, `pinStatus`, never the secret or the digest, legacy plaintext included). `buildTriggerConfig` also refuses a non-boolean `enabled` and turns a vanished profile file into an error instead of a throw. `patchTrigger` accepts a closed field list (unknown fields, `webhookSecret` included, are refused; `everyMinutes: null` clears the schedule, while `null` for `dedupWindowMs` / `maxActiveTasks` is refused: it would skip the defaults and be saved as is) and renews the pin only when `profile` changes or on `{ repin: true }`: a toggle or rename of a trigger whose profile drifted or vanished still works, and never silently accepts the drift.
- **Triggers belong to long-term agents.** `trigger.profile` is the agent name, with no `cwd`: runs happen in `triggerHome` (the agent home). The pin and every re-resolution (`triggerPinStatus`, `resolveIn`, `startAgentProfileRun`) use the GLOBAL profile (`resolveLongTermProfile`): the agent can write its home, so a `<home>/.pi/agents/<name>.md` must never shadow it. Scheduled fires create a `target: "thread"` task with the raw template (nothing external in it); webhook payloads stay `isolated` and fenced. An isolated run passes `agentProfileTools` (the allowlist) with no trust; `startRpcSession` then also resolves globally and only in the agent home, and applies the override to new sessions only. `PATCH /api/agents/[name]` re-pins the agent's triggers (`repinTriggersOfAgent`), `DELETE` removes them first.
- **Profile drift is visible.** `triggerPinStatus` (`trigger-store.ts`, the scheduler's admission check, never throws: an unresolvable or unreadable profile is `missing`) feeds `pinStatus: "ok" | "drift" | "missing"` on every public trigger. The row shows a translated badge saying fires are refused; a `drift` row gets a Re-pin button (confirm, then `PATCH { repin: true }`). `repin` re-resolves the agent's global profile and re-runs the creation check (`validateTriggerProfile`): a profile that is no longer long-term is refused and the old pin stays. `missing` has no button: restore the profile or edit the trigger. History is the tasks list filtered by `triggerId` on the client; triggers are loaded and polled every 10 s by `AgentSpaceLeft`. The secret dialog keeps the secret in React state only and closes on Escape, not on a backdrop click.
- **Pause** (`settings.paused`, `pausedAgents`): scheduler skips, webhook 503 (no token consumed), selectors skip, thread runs refuse, running tasks of the scope are aborted when the pause is set; user turns are never blocked. Quarantine (`lib/agents/quarantine.ts`) sets `pausedAgents` first, then also cancels the agent's queued tasks (a plain pause lets them wait); the pause stays until resumed.
- **Run registry** (`run-registry.ts`): `~/.pi/agent/agent-ops/runs.jsonl`, one line per run (tasks through the runner, user turns of trusted threads through the wrapper), usage counted by `run-usage.ts` from the run's own events; `billing` (`subscription` for `claude-bridge`, `api` for any other provider, `unknown` without one) and `costEquivalent` (subscription only, `priceRecord()` in `lib/cost-equivalent.ts`, shared by the runner and the thread tracker) sit beside `usage.cost`, never summed into it; rotated past 10 MiB; `task.usage` holds the same numbers, except when a cancel won the terminal write: then it is absent and the registry is the source of truth. Exported to Grafana by promtail/Alloy, never by a scrape of the sessions. A thread event turn is recorded by the runner only: the wrapper skips its user-turn record only for a turn started by the runner's own prompt (`origin: "agent-ops"`, counted in `pendingRunnerPrompts`), never because a task is `running`. A run whose terminal write lost to a cancel is still recorded, with the winning status.
- **Health gauges** (`health.ts`, `GET /api/agent-ops/health`, dot under `+` in `AgentRail`). Pure `collectHealth` / `healthLevel` over: `globalThis.__agentOpsLastTick` (set as the last statement of every `runSchedulerTick`, paused or failed included), both runners' `runningCount`, `countAliveRpcSessions()`, `memAvailableMb()`, `settings.paused`, and `getExtensionErrorStatuses()` (alive wrappers' extension statuses starting with "error"/"failed"). `down`: last tick over 3 min old; `warn`: no tick yet (the first tick comes 60 s after `startScheduler`, so a fresh process is not red), extension errors, `freeMb < 1500` or paused; else `ok`. The rail polls every 30 s while visible. RAM, services and TCP probes are node_exporter's job.
- **Quiet hours, `notBefore`, critical, daily fires** (Task 18, `quiet-hours.ts`, `scheduler.ts`, `lib/agents/queue.ts`). Everything is the **server's local clock** (no timezone is configured). `settings.quietHours { from, to }` crosses midnight when `from > to`; `from === to` is no window. `inQuietHours` / `quietHoursEnd` (next `to` boundary) / `dailyBucket(at, now)` (`YYYY-MM-DD` once today's `at` passed) are pure. The tick reads the settings once. Scheduled fires (interval and daily) inside the window are skipped unless `trigger.critical`, journaled `refused` / `quiet hours` once per bucket (`logRefusalOnce`, keyed per trigger and fire kind, so interval and daily fires do not flip each other; the dedup key of a refusal is the bucket, except day-scoped reasons `daily token budget reached` / `daily cost budget reached` / `daily run cap reached`, keyed on the local date, and `quiet hours`, keyed on `quietHoursEnd`'s ISO string: one line per day or window instead of up to 1440 a day with `everyMinutes: 1`); their tokens are not claimed, so the fire happens at the first tick after the window. Webhook ingestion (after the secret check and the dedup token) still creates its task inside the window but with `notBefore = quietHoursEnd` (journal `accepted`, reason `deferred to quiet hours end`), unless `trigger.critical` or the `severity` argument is `"critical"` (Task 19 supplies it from the payload). `fireTriggerNow` ignores quiet hours (a person asked). **A waiting task holds no cap slot**: `activeTaskCount` counts running tasks and queued ones with no `notBefore` or a past one; both selectors skip a task whose `notBefore` is in the future (`isWaiting`), so it starts on the first kick after the deadline. `dry-run` adds `deferredUntil` when the plan would be deferred, and applies `agent paused` only to an otherwise accepted plan (admission and cap reasons win). **Daily fires**: a trigger with `at: "HH:MM"` (may coexist with `everyMinutes`; both fire) claims `<id>.daily.<YYYY-MM-DD>` (local date) once its time passed and creates the task like a scheduled fire; `fireReason.daily` carries the date and `bucket` the local midnight in ms. `purgeStaleFireTokens` deletes daily tokens after 48 h. `critical` and `at` are cleared with `null` in a PATCH. Consistency: a schedule fire of a trigger with a webhook secret runs isolated from the raw template (as `dry-run` reports). UI: `TriggerDialog` (Daily at, Critical), `TaskRow` "Waits until HH:MM", 🌙 on the rail (`health.quietHours`), Settings › Agents `AgentOpsSettings` (quiet hours, run cap 1..8, memory floor, saved through `/api/agent-ops/settings`).
- **Quiet-hours digest** (Task 21, `digest.ts`, `sendDigestIfDue` in `scheduler.ts`). One push per day when quiet hours end: after the trigger loop, if `settings.quietHours` is set, the tick is outside the window and `now` is within **60 minutes after today's `to`**, it claims `<triggersDir>/digest.<YYYY-MM-DD>` (wx, 0o600; purged after 48 h by `purgeStaleFireTokens`). `buildDigest` counts terminal tasks (completed, failed, cancelled) with `completedAt >= since`, `since = to - window length` (window length `to - from`, +24 h when it crosses midnight); `byAgent` has runs, failed and cards (isolated runs that completed or failed); agentless tasks group under `"?"`. `digestBody` is deterministic text from `agents.push.digest` (`{runs}`, `{failed}`, `{agents}` sorted), never a model call. The token is claimed even when nothing ran (`runs === 0` pushes nothing: one check per day). Tag `pi-digest:<date>`, url `/`. **Limitation**: a server down or a tick missed for more than 60 minutes after `to` skips that day's digest (the token is never claimed, nothing catches up). `runSchedulerTick(kick, create, { notify })` is the test seam (default `notifyAgent`); `localeText` gained the key `agentsDigest`.
- **Payload formats** (Task 19, `payload-formats.ts`, `planIngestion`). `trigger.payloadFormat` (`raw` default | `alertmanager` | `grafana`; PATCH `null` clears) picks a pure `mapPayload(format, body)` that runs inside ingestion, after the secret check; the fenced prompt wraps the MAPPED text, so external data stays data. `raw` is `payloadText` (the `text` string, else JSON). `alertmanager` (v4) and `grafana` (unified alerting) read `alerts[]`: one line per alert `status severity alertname instance: summary` (`description` when no summary, missing fields omitted, `startsAt` never in the text). `dedupKey = status:sorted fingerprints` (labels JSON when a fingerprint is absent) replaces the body in `payloadHash`, so a re-notification differing only in `startsAt` is `duplicate within dedup window`. `severity` = the highest of `critical > warning > info` over the **firing** alerts only (other values ignored; a `resolved` alert never contributes, so a resolved critical cannot bypass quiet hours; an alert without `status` counts); `"critical"` bypasses quiet hours like `trigger.critical` (plan `severity`, also honored by `dry-run`'s `deferredUntil`). A body that is not an object, or has no `alerts` array or an empty one, maps to raw text; a mapper that throws falls back to raw (`plan.formatFallback`) and the accepted journal line carries `reason: "payload format fallback"` (a quiet-hours deferral reason wins). UI: `TriggerDialog` "Payload format" select (webhook triggers), `hookCurl(origin, id, secret, format)` shows an example body per format. GitHub has no mapper: call the hook from a GitHub Actions step with the secret header (no HMAC verification).
- **Daily run cap and usage** (Task 20, `scheduler.ts`, `task-list.ts`). `trigger.maxRunsPerDay` (integer ≥ 1, absent = unlimited; PATCH `null` clears) refuses with `daily run cap reached` once `runsTodayCount(triggerId, now)` ≥ the cap. The count is every task of the trigger (any status: a cancelled run was still a run) with `createdAt` ≥ the **server's local midnight**, from `listTasks()`; it resets at the next local midnight. Applied after the `maxActiveTasks` check and before any token on all three fire paths: `planIngestion(…, runsToday = 0)` (webhook ingestion and `dry-run`, so a refused payload keeps its dedup token), `fireTriggerNow` and `fireScheduled` (interval and daily; journaled `refused` once per bucket through `logRefusalOnce`). Check-then-act across processes, like the active cap. `shapeTaskList` adds `costEquivalent` (from `priceRecord`, subscription providers with a known price only) to a list item that carries `usage`, so the client never prices; the panel shows `3 turns · 12k tok · $0.04` or `≈ $0.04 API-equivalent`, never the sum of both. The trigger row shows `today 3/10 runs` from the loaded tasks (same midnight rule, approximate past the 200-task list limit).
- **Retry is a new task** (`POST /api/agent-ops/tasks/[id]` with `{ action: "retry" }`; `{ message }` still steers, both in one body is a 400). Terminal states stay immutable, so a retry copies `profile cwd prompt title origin triggerId pinnedProfileSha256 agent target kind model tools maxRunMs` into a fresh queued task with `retryOf: <id>`, `attempt: (attempt ?? 1) + 1` and `fireReason: { source: "manual" }`; `notBefore` is NOT copied (a retry runs now). 409 when the source is queued/running. For a trigger task the pin is re-checked first: trigger removed or `triggerPinStatus === "drift"` → 409, so a drifted profile never runs a trigger task. The stored prompt is reused (a webhook task keeps its fenced payload). The trigger's journal gets `{ source: "manual", verdict: "accepted", taskId, reason: "retry of <shortId>" }`. - **Daily budget** (Task 24, `budget.ts`, `budget-push.ts`, `budgetRefusalFor` in `scheduler.ts`). `spentToday(records, now)` sums the agent's `runs.jsonl` records since the **server's local midnight**: tokens = input + output + cacheRead + cacheWrite, cost = provider `usage.cost` only, never `costEquivalent`. `budgetRefusal(agent, spent)` answers `daily token budget reached` when `budgetTokensPerDay` is set and `tokens >= budget`, else `daily cost budget reached` for `budgetUsdPerDay` (tokens for subscriptions, dollars for API billing; either or both may be set; **a budget of 0 blocks at once**, the user's explicit choice). **Enforced on the three automatic paths only**, right after `admissionRefusal` and before quiet hours, any cap or dedup token (`fireScheduled` too, so the journal reason is the budget): `planIngestion(…, budget)` (webhook ingestion and `dry-run`, so a refused payload keeps its token), `fireTriggerNow` (chained reason) and `fireScheduled` (journaled `refused` once per bucket through `logRefusalOnce`). `runSchedulerTick` reads the registry once per tick, lazily on the first budgeted agent, and shares the per-agent totals (`spentOf`); the other paths read the agent's records of the day. **Re-checked at run start (Checkpoint C)**: creation-time admission is not enough, since quiet hours can queue many waiting tasks that all drain at once. `kickRunner` first calls `failOverBudgetTriggerTasks()` (`budget-gate.ts`, `overBudgetTriggerTasks` is the pure part): every queued `origin: "trigger"` task whose agent is over budget (asked once per agent) is set `failed` with the budget reason as `error` and gets one `refused` journal line (`source` from `fireReason.source`), so nothing stays queued to fire after the budget is reached; it does not push (no flood). `assertTaskStillStartable` (isolated) and `startThreadEventRun` (right before the send, beside the pause check) throw the same reason for a trigger task, the belt for a race. Running tasks are not aborted. **Deferred bound**: `ingestTriggerPayload` refuses a payload that would be deferred with `too many deferred tasks for this trigger` (journaled, no token) once the trigger already has `MAX_DEFERRED_PER_TRIGGER = 20` queued tasks with a future `notBefore`; critical payloads are never deferred and are not counted against it. **Never blocked**: UI-queued tasks (`POST /api/agents/[name]/tasks`) and user turns in the thread. Check-then-act: the run that crosses the budget finishes (no mid-run abort), the next automatic fire is refused. **Push on crossing**: `handleTaskEnd` calls `pushBudgetReachedOnce(agent)` after every terminal run (the record is already written); when the budget is reached it claims `<triggersDir>/budget.<agent>.<YYYY-MM-DD>` (wx; purged after 48 h with the digest tokens) and pushes `agents.push.budget` (`{name}`, `{kind}` = tokens | cost), url `/?agent=<name>`, tag `pi-agent-budget:<name>:<date>`: one push per agent per local day. `localeText` gained `agentBudget`; `pushBudgetReachedOnce(name, { notify, now })` is the test seam.
